# Track B — Engineering Practice & Mentorship

- **Status:** Active as an optional learning track
- **Created:** 2026-10-10
- **Companion:** [Track A — Feature Delivery Lifecycle (FDL v1.0)](../workflows/feature-delivery-lifecycle.md)
- **Audience:** Solo developer growing toward Technical Lead, and future team leads
- **Security:** This repository is public. Use fictional or sanitized examples only.

## Two tracks, one knowledge base

| Track | Purpose | Default behavior | Completion |
| --- | --- | --- | --- |
| **A — Build My Engineer** | Design, review and evolve practical engineering workflows, ownership, artifacts and quality gates | **Default** when discussing the project | Workflow accepted based on usefulness and review |
| **B — Practice & Mentorship** | Understand *why/how* the same activities work; practice decisions under uncertainty | **Opt-in**: only when explicitly requested | Reflection and applied learning, **not** a prerequisite for Track A |

Practicing never blocks implementing an approved workflow. Do not transform a mentorship exercise into a new engineering rule or a Skill without separate agreement.

## How to ask for mentorship

Natural requests work:
- "วิท เข้า Track B: Requirement Discovery ต่อจากที่ค้าง"
- "วิท mentor กูเรื่อง Solution Design แบบ role-play"
- "วิท ขอ case study เรื่อง Architecture Trade-offs แล้ว review คำตอบกู"
- "วิท สลับกลับ Track A ออกแบบ workflow ต่อ"

When entering Track B, the mentor should:
1. Identify the selected module and learning objective.
2. Ask whether to **continue the last case**, use a **new case**, or **explain first** only if unclear; otherwise follow the user's stated preference.
3. Provide at most one focused question at a time in interactive practice; give candid feedback and counterexamples.
4. Distinguish user statements, hypotheses, evidence, and recommendations.
5. End a session with an optional brief recap and next practice step; never silently mark exercises complete.

When returning to Track A, resume engineering design directly, not a quiz.

## Practice progress and privacy

- Git documents contain **curriculum and sanitized sample cases**, not private chat transcripts or user-specific performance notes.
- Progress is **not automatically inferred** from a chat and is not tracked in this public repository.
- If the learner wants persistent progress, explicitly ask for an opt-in, sanitized progress note or keep it in a private location.
- To resume an earlier case in a new session, reference its module and include the prior case or ask the assistant to retrieve past context where supported.

## Definition of a useful practice

Each exercise should answer:
- **Capability:** What engineering decision or behavior is being trained?
- **Scenario:** What realistic context is available?
- **Exercise:** What should the learner decide or produce?
- **Review rubric:** What makes an answer robust, and what risks are often missed?
- **Transfer:** How does this help with a real workflow?

Prefer simple examples over large curricula. Do not create an AI Skill just to run a lesson.
