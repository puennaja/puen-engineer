## ผู้เขียนพูดเรื่องอะไรบ้าง (เฉพาะส่วนที่ตรวจได้)

### แนวคิดเปิดบท: ไม่ใช่ทุกอย่างสำคัญเท่ากัน

การออกแบบ Software ที่ดีคือ **แยกสิ่งที่คนใช้ระบบต้องรู้ ออกจากรายละเอียดที่ไม่จำเป็น** แล้วทำให้สิ่งสำคัญเด่นชัด เช่น Contract, Invariant หรือความสามารถหลัก ส่วนรายละเอียด Implementation ควรถูกซ่อนอยู่หลัง Module

แม้แต่ Naming หรือการ Optimize Performance ก็ต้องตัดสินใจว่าเรื่องใดสำคัญสำหรับคนที่ต้องดูแลหรือใช้ระบบ

### §21.1 — มองหา Leverage (ตรวจได้บางส่วน)

แนวคิดที่มี **Leverage** คือรู้เรื่องเดียวแล้วช่วยแก้หรือเข้าใจได้หลายเรื่อง เช่น API จัดการข้อความแบบเพิ่ม/ลบช่วงตัวอักษร ใช้งานได้หลากหลายกว่าการทำ Method แยกสำหรับปุ่ม Backspace โดยเฉพาะ ผู้เขียนยังกล่าวถึง Invariant ในฐานะจุดที่ช่วยให้เราคาดเดาพฤติกรรมระบบได้

**หมายเหตุ:** ได้จากส่วนข้อความที่ระบบค้นหาแสดง ยังไม่ได้ตรวจ §21.1 ทั้งส่วน

### §21.3 — ทำให้สิ่งสำคัญมองเห็นชัด

ผู้เขียนอธิบายสามวิธี:
- **Prominence:** สิ่งสำคัญควรอยู่ในตำแหน่งที่คนมองเห็น เช่น ชื่อ, Interface, Documentation
- **Repetition:** แนวคิดสำคัญปรากฏซ้ำอย่างมีความหมาย
- **Centrality:** Contract สำคัญควรเป็นแกนที่โครงสร้างอื่นอ้างอิง เช่น Interface ของ Device Drivers

ในทางกลับกัน รายละเอียดที่ไม่สำคัญไม่ควรถูกกระจายซ้ำทั่ว Codebase หรือกลายเป็นตัวกำหนด Architecture

### §21.4 — ความผิดพลาดสองแบบ

**หนึ่ง เปิดเผยรายละเอียดมากเกินไป:** API บังคับให้ทุก Caller ระบุสิ่งที่แทบไม่มีใครต้องเลือก เช่น Buffered/Unbuffered I/O จนทำให้ Cognitive Load สูงขึ้น

**สอง ซ่อนสิ่งสำคัญเกินไป:** ผู้ใช้ไม่เห็น Contract, ข้อจำกัด หรือความสามารถที่จำเป็น จนต้องเดาและเขียนซ้ำเอง

**สรุป:** ไม่ใช่ซ่อนทุกอย่าง แต่ต้อง **ซ่อนสิ่งที่ไม่จำเป็น และเผยสิ่งที่จำเป็น**

## ตัวอย่างจาก My Engineer (ไม่ใช่ตัวอย่างจากหนังสือ)

## Candidate Principles — ยังไม่ Approved

### AP-C05 — เปิดเผย High-leverage Invariants และ Contracts

- **Understanding:** ทำให้แนวคิดสำคัญและ Invariant ที่ผู้ใช้ต้องรู้ปรากฏอย่างชัดเจน
- **Judgment:** เหมาะกับ API, Domain Boundary และ Documentation แต่อย่าเลือก Abstraction กลางก่อนมีหลักฐานว่ามันคงตัวจริง
- **Evidence:** ช่วงเปิดบท, §21.1 ที่เข้าถึงได้ และ §21.3 จาก Official Extract
- **Overlap:** EF-G03 และ AP-C02 ต้องตรวจว่าควรรวมกันไหม

### AP-C06 — ซ่อนรายละเอียดไม่จำเป็น แต่อย่าซ่อนเงื่อนไขสำคัญ

- **Understanding:** ลดข้อมูลที่ Caller ต้องรับรู้โดยซ่อน Implementation และทำ Default ให้สมเหตุสมผล
- **Judgment:** ต้องเปิดเผย Failure Behavior, Side Effects, Security Constraints และ Business Invariants ที่จำเป็น
- **Evidence:** ช่วงเปิดบทและ §21.4 จาก Official Extract
- **Overlap:** AP-C01, AP-C02 และ EF-G08
