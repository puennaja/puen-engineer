## 1. ใจความหลักของ Part I

**[ผู้เขียน/เนื้อหาจริง + สำนักพิมพ์]** การพัฒนา Software ในฐานะวิศวกรรม ไม่ใช่แค่การเขียนโค้ดหรือทำตามกระบวนการ แต่ต้องจัดการความไม่แน่นอนอย่างมีวินัย โดย Farley เน้นความสามารถพื้นฐานสองด้าน:

1. **เก่งเรื่องการเรียนรู้ (Experts at Learning):** สำรวจ ตั้งสมมติฐาน ทดลอง และใช้หลักฐานจริง เพื่อเข้าใจว่าอะไรใช้ได้ในสภาพแวดล้อมที่เปลี่ยนตลอดเวลา
2. **เก่งเรื่องการจัดการความซับซ้อน (Experts at Managing Complexity):** ระบบ Software ใหญ่เกินกว่าจะเข้าใจทุกอย่างพร้อมกันได้ ความซับซ้อนเกิดทั้งจากโค้ดและการทำงานร่วมกันของคน

**[My Engineer/สังเคราะห์]** คำถามในการตัดสินว่า Process ดีหรือไม่ ไม่ควรเป็นแค่ “มีเอกสารกี่ฉบับ” หรือ “ทำตามขั้นตอนครบไหม” แต่ควรถามว่า **ทีมเรียนรู้ได้ดีขึ้นไหม และการเปลี่ยนระบบเข้าใจง่าย ปลอดภัยขึ้นไหม**

อย่าตีความว่าสามารถใช้ตัวเลขเดียววัดคุณภาพวิศวกรรมทั้งหมดได้

## 2. สรุปแยกตามบท

### บทที่ 1 — Introduction (ภาพรวมหัวข้อ ยังไม่ได้อ่านตัวบทครบ)

**ระดับหลักฐาน: [สำนักพิมพ์/สารบัญ]** เนื้อหาที่ระบุในสารบัญเกี่ยวกับการใช้วิทยาศาสตร์แก้ปัญหาจริง ความหมายและประวัติศาสตร์ของ Software Engineering และการเปลี่ยนวิธีคิดในการทำงาน

**[My Engineer/สังเคราะห์]** คำถามที่เราอยากค้นต่อ: อะไรคือหลักฐานว่าเรากำลังแก้ปัญหาอย่างเป็นวิศวกรรม ไม่ใช่แค่เขียน Code ได้เร็ว?

**[รอตรวจสอบ]** คำนิยามเฉพาะ ตัวอย่างทางประวัติศาสตร์ และเหตุผลโดยละเอียดต้องอ่านตัวบทเต็มก่อนจะอ้างเป็นมุมมองของ Farley

### บทที่ 2 — What Is Engineering? (ภาพรวมหัวข้อ ยังไม่ได้อ่านตัวบทครบ)

**ระดับหลักฐาน: [สำนักพิมพ์/สารบัญ]** หัวข้อมีความต่างระหว่าง Design Engineering กับ Production Engineering, การเขียนโค้ดกับงานวิศวกรรม, ข้อจำกัดของ Craftsmanship, การวัดผล, ความแม่นยำ, ความซับซ้อน, Trade-offs และภาพลวงว่ามีความคืบหน้า

**[My Engineer/สังเคราะห์]** ตัวอย่างคำถาม: งานอะไรช่วยลดต้นทุนและความเสี่ยงของการเปลี่ยนระบบ แม้ไม่ได้ผลิตโค้ดจำนวนมาก? เช่น ตรวจ Contract, พิสูจน์สมมติฐาน หรือหาวิธี Recovery

**[รอตรวจสอบ]** เรายังไม่ควรสรุปจุดยืนละเอียดของ Farley เรื่อง Craft หรือ Productivity เพราะยังไม่อ่านเนื้อหาบทที่ 2 ทั้งหมด

### บทที่ 3 — Fundamentals of an Engineering Approach

**ระดับหลักฐาน: [ผู้เขียน/เนื้อหาจริง]** จากตัวอย่างบทที่ 3 หน้า 31–38 ที่สำนักพิมพ์เปิดให้อ่าน

**A. หลักการที่ใช้ได้นาน สำคัญกว่าแค่เทคโนโลยีที่กำลังฮิต** Farley ชวนตั้งคำถามว่าการเปลี่ยนเทคโนโลยีหรือกระบวนการทุกครั้งเป็นความก้าวหน้าจริงไหม เขาพยายามหาหลักการพื้นฐานที่ยังใช้ได้แม้เครื่องมือเปลี่ยน **[My Engineer]** เราจึงควรเลือก Practice จากปัญหาที่แก้ ไม่ใช่ความนิยม

**B. ใช้การวัดผลเพื่อช่วยตัดสินใจ** Farley แยกการวัด Productivity ของบุคคลที่ทำได้ยาก ออกจากการวัดสิ่งที่มีประโยชน์ในระบบการส่งมอบงาน โดยยกมุมมอง **Stability** และ **Throughput** ซึ่งต้องพิจารณาควบคู่กัน **[My Engineer]** ตัวเลขเหล่านี้ไม่ได้บอกว่าผลิตภัณฑ์มีคุณค่าหรือ Engineer คนใดเก่งกว่าใคร

**C. เรียนรู้ด้วยหลักฐาน ไม่ใช่ความมั่นใจ** แนวคิดแบบวิทยาศาสตร์คือสังเกต ตั้งข้อสันนิษฐาน และทดสอบ ไม่ถือว่าความเห็นของผู้มีประสบการณ์คือข้อเท็จจริงโดยอัตโนมัติ **[My Engineer]** ใน Technical Discovery เราจึงควรแยก Confirmed, Assumed, Unknown และ Evidence

**D. จัดการความซับซ้อนอย่างตั้งใจ** ระบบขนาดใหญ่ไม่สามารถอยู่ในหัวคนคนเดียวทั้งหมด และความซับซ้อนมีทั้งด้าน Technical และ Organization **[My Engineer]** การกำหนด Boundary และ Ownership ที่ดีอาจช่วยได้ แต่ไม่ใช่แปลว่าต้องเพิ่ม Layer หรือแยก Microservice เสมอ

**E. เป็นความสามารถ ไม่ใช่สูตรสำเร็จ** หนังสือมอง Learning กับ Managing Complexity เป็นแกนของการทำงาน ไม่ใช่สั่งให้ทุกบริษัทต้องใช้ Method หรือ Architecture เดียวกัน

## 3. Candidate Principles — ยังไม่ใช่กฎที่ Approve แล้ว

### EF-C01 — ตัดสินใจจากหลักฐาน ไม่ใช่แค่ความมั่นใจ

- **ประเภท:** Candidate Principle ตั้งชื่อและสังเคราะห์โดย My Engineer อิงแนวคิด Empirical Learning จากบทที่ 3
- **Definition:** เมื่อมีความไม่แน่นอนสำคัญ ให้หาหลักฐานที่ตรวจสอบได้หรือทดลองแบบจำกัดขอบเขตก่อนสรุป
- **Why / Mechanism:** การตั้งสมมติฐานที่ทดสอบได้ ทำให้เราพบว่าความเข้าใจเดิมผิดตรงไหน
- **When to Apply:** Requirement ยังคลุมเครือ, Debug ระบบที่ไม่คุ้น, Design Decision ที่มีผลกระทบสูง
- **When Not to Apply:** งานเล็กและความเสี่ยงต่ำไม่จำเป็นต้องทำเอกสารการทดลองยาว ๆ
- **Trade-offs:** ใช้เวลาและต้นทุนเพิ่ม อีกทั้งการวัดผิดหรือเลือกข้อมูลลำเอียงอาจพาไปผิดทาง
- **Failure Modes:** เลือกแต่ข้อมูลสนับสนุน, Benchmark ที่สร้างขึ้น, เอาผล Spike ครั้งเดียวมาเหมารวม
- **Alternative:** งานที่เข้าใจดีและแก้ย้อนกลับง่าย อาจใช้ Pattern เดิมพร้อมตรวจสอบสั้น ๆ
- **ตัวอย่างสมมติ:** ก่อนสร้างระบบ Import CSV ของแอปการเงิน ให้ทดลองไฟล์จำลองที่มีรายการซ้ำและรูปแบบวันที่แตกต่างกัน
- **Sources:** [S2] บทที่ 3 หน้า 31–38, [S3]
- **Confidence:** ปานกลางเฉพาะการเชื่อมกับหัวข้อจากหนังสือ; ยังไม่ได้ตรวจงานวิจัยอิสระให้ครบ
- **Related Workflows (เสนอ):** Requirement Discovery, Technical Discovery, Solution Design
- **Status:** Candidate

### EF-C02 — จัดการความซับซ้อนเพื่อให้ระบบเปลี่ยนได้ง่าย

- **ประเภท:** Candidate Principle ตั้งชื่อและสังเคราะห์โดย My Engineer อิงหัวข้อ Complexity จากบทที่ 3
- **Definition:** ออกแบบ Responsibility และ Boundary ให้พฤติกรรมสำคัญเข้าใจ ทดสอบ และเปลี่ยนแปลงได้อย่างปลอดภัย
- **Why / Mechanism:** ลดสิ่งที่ต้องเข้าใจหรือประสานพร้อมกันทุกครั้งที่แก้ระบบ
- **When to Apply:** ระบบโตขึ้น, หลายทีมทำงานร่วมกัน, Ownership ของข้อมูลไม่ชัด, แก้จุดหนึ่งกระทบหลายส่วน
- **When Not to Apply:** Prototype ชั่วคราวหรือระบบเล็กมาก อาจไม่คุ้มกับโครงสร้างที่ซับซ้อน
- **Trade-offs:** Abstraction เพิ่มทางอ้อมให้ต้องไล่ตามและอาจเพิ่ม Coordination
- **Failure Modes:** สร้าง Interface ทุก Class, แยก Service ตามกระแส, แบ่ง Module โดยไม่มี Boundary จริง
- **Alternative:** ใช้ Module ที่ Cohesive และ Dependency ตรงไปตรงมา จนกว่าจะพบเหตุผลชัดให้แยก
- **ตัวอย่างสมมติ:** แยกการอ่านรูปแบบ Statement ของธนาคารออกจากกฎคำนวณรายจ่าย แต่ยังไม่จำเป็นต้องแยกเป็น Service ใหม่
- **Sources:** [S2] บทที่ 3 หน้า 36–38; เนื้อหาเชิงลึกเรื่อง Modularity ใน Part III **ยังไม่ได้ตรวจในรอบนี้**
- **Confidence:** ปานกลางสำหรับภาพรวม ต้องศึกษาบทเกี่ยวกับ Design และแหล่งอิสระเพิ่ม
- **Related Workflows (เสนอ):** Technical Discovery, Solution Design
- **Status:** Candidate

## 4. ข้อควรระวัง / คำถามที่ต้องทบทวน

1. **Measurement มีบริบท:** Stability และ Throughput ช่วยมองการส่งมอบ แต่ไม่ได้ยืนยันว่าเราสร้างสิ่งที่ผู้ใช้ต้องการ
2. **Experiment หลอกเราได้:** ใครกำหนดเกณฑ์ผ่าน? ชุดข้อมูลมีอคติหรือไม่?
3. **Complexity ไม่หายเพราะเพิ่ม Layer:** Boundary ที่เลือกช่วยลดต้นทุนในการเปลี่ยนจริงไหม?
4. **ไม่ต้องสร้างพิธีการเกินจำเป็น:** งานความเสี่ยงต่ำต้องใช้หลักฐานขั้นต่ำแค่ไหน?
5. **หนังสือมีอายุ:** เล่มนี้เผยแพร่ปี 2021 จึงต้องตรวจความเหมาะสมกับหลักฐานสมัยใหม่และผลทดลองของเรา ไม่รับเป็นกฎอัตโนมัติ
