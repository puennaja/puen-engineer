## สรุปภาพใหญ่

**[จากหนังสือ]** Software Engineering ไม่ได้จบเมื่อเขียน Code เสร็จ แต่รวมถึงความสามารถในการ **รักษาและเปลี่ยน Software ตลอดช่วงชีวิตที่มันยังมีประโยชน์** การทำงานร่วมกันเมื่อ **ระบบและจำนวนคนขยายตัว** และการเลือกทางออกท่ามกลาง **Trade-offs** ที่มักมีข้อมูลไม่ครบ

**[My Engineer]** Framework ของเราไม่ควรวัดความดีจากจำนวนเอกสาร จำนวนพิธีการ หรือความเร็วในการให้ AI เขียนโค้ด แต่ควรช่วยให้ตัดสินใจได้เหมาะสม แก้ไขการตัดสินใจได้ และรองรับการเปลี่ยนแปลงโดยไม่เสียต้นทุนเกินจำเป็น

## 1. Programming ต่างจาก Software Engineering อย่างไร

**[จากหนังสือ — ช่วงเปิดบท]** ผู้เขียนเสนอสามมิติ: **Time, Scale, Trade-offs**

- **Time:** โค้ดใช้ครั้งเดียว กับโค้ดที่ต้องดูแลเป็นสิบปี ไม่ควรใช้กฎเดียวกันทั้งหมด
- **Scale:** ระบบไม่ได้มีแค่จำนวน Requests หรือ CPU แต่ยังมีจำนวน Engineer, ทีม, Dependencies และต้นทุนการประสานงาน
- **Trade-offs:** เราตัดสินใจภายใต้ข้อจำกัดและข้อมูลที่ไม่สมบูรณ์ ไม่ใช่แค่เลือกเทคนิคที่ดูดี

คำว่า **Sustainability** ในบริบทนี้หมายถึง “ยังมีความสามารถเปลี่ยนระบบได้เมื่อมีเหตุผลที่คุ้มค่า” ไม่ได้หมายความว่าต้องอัปเกรดทุก Dependency ตลอดเวลา

**[My Engineer]** ก่อนออกแบบ Standard ให้ถามก่อนว่าระบบคาดว่าจะอยู่กี่ปี ใครดูแล และการเปลี่ยนอะไรมีราคาแพง ตัวทดลอง Parse CSV แบบใช้ครั้งเดียวไม่จำเป็นต้องใช้มาตรฐานเข้มเท่าระบบ Ledger ที่ต้องทำงานอีกหลายปี

## 2. Time and Change — อนาคตทำให้โค้ดที่เคยใช้ได้อาจกลายเป็นปัญหา

**[จากหนังสือ]** โครงการที่เริ่มจาก “แค่ให้รันได้” อาจมีชีวิตยืนยาวกว่าที่คิด เมื่อ Dependency, OS, Language หรือ Business Requirements เปลี่ยน ก็ต้องกลับมาแก้ สิ่งที่ไม่ได้อัปเกรดนานจะยิ่งเปลี่ยนยากเพราะมีสมมติฐานที่ฝังลึก คนไม่เคยทำ และขนาดการเปลี่ยนใหญ่ขึ้น

ผู้เขียนไม่ได้บอกให้ Upgrade เพื่อความใหม่ แต่ให้ **รักษาความสามารถในการ Upgrade** เพราะวันหนึ่ง Security, Hardware หรือข้อกำหนดทางธุรกิจอาจบังคับให้เปลี่ยน

### Hyrum’s Law — พฤติกรรมที่มองเห็นอาจกลายเป็นสัญญาโดยไม่ตั้งใจ

**[จากหนังสือ]** เมื่อ API มีผู้ใช้มากพอ จะมีบางคนพึ่งพาพฤติกรรมที่เห็นได้ แม้ไม่ได้อยู่ใน Contract ทางการ

**ตัวอย่าง Hash Ordering:** Hash Set อาจไม่มีสัญญาว่าจะเรียงข้อมูลอย่างไร แต่ผู้ใช้บางรายอาจเห็นว่ามันออกลำดับเดิมแล้วเขียนโค้ดพึ่งพาลำดับนั้น หาก Runtime เปลี่ยน ลำดับเปลี่ยน ก็เกิด Regression ได้ แม้ผู้พัฒนาไม่ได้ผิดสเปก

**[My Engineer]** ตอนทำ Technical Discovery ต้องตรวจ **Consumer จริงและพฤติกรรมที่เคยเกิดขึ้น** ไม่ใช่อ่าน OpenAPI หรือ Interface แล้วสรุปว่าปลอดภัยทั้งหมด และตอน Solution Design ควรพิจารณา Contract Tests หรือแผน Migration สำหรับการเปลี่ยนที่เสี่ยง

**ข้อจำกัด:** ไม่ได้แปลว่าต้องรักษา Bug หรือพฤติกรรมผิดสเปกทุกอย่างไปตลอด แต่ต้องเข้าใจผลกระทบก่อนเปลี่ยน

### Why Not Just Aim for “Nothing Changes”?

**[จากหนังสือ]** การไม่เปลี่ยนก็มีต้นทุน เช่น ช่องโหว่ Security, Dependencies เก่า หรือการเสียโอกาสด้านประสิทธิภาพ ผู้เขียนแยกชัดระหว่าง **เลือกไม่เปลี่ยนเพราะไม่คุ้ม** กับ **เปลี่ยนไม่ได้เลย**

## 3. Scale and Efficiency — กระบวนการทำงานเองก็ต้อง Scale

**[จากหนังสือ]** เมื่อองค์กรโต สิ่งที่ต้องทำซ้ำจะมีต้นทุนเพิ่ม ทั้ง Build, Test, Upgrade, ติดต่อหลายทีม และการแก้ Dependencies หากต้นทุนต่อกิจกรรมเพิ่มเร็วเกินขนาดองค์กร ระบบส่งมอบงานจะยั่งยืนยาก ปัญหามักสะสมช้า ๆ จนคนคุ้นชิน

### Policies That Don't Scale — Churn Rule

Google ยกกรณีทีม Infrastructure ออกเวอร์ชันใหม่แล้วสั่งทุกทีมย้ายเอง แต่ละทีมต้องเรียนรู้วิธีแก้ซ้ำกันจำนวนมาก

**Churn Rule** เป็นแนวทางที่ให้เจ้าของ Infrastructure ช่วย Migration ให้ผู้ใช้ภายในหรือเปลี่ยนอย่างเข้ากันได้ย้อนหลังเพื่อลดภาระรวม

อีกกรณีคือ Long-lived Feature Branches ที่ทำให้การ Sync และ Merge ยิ่งหนักเมื่อจำนวนงานขนานเพิ่ม

**[My Engineer]** การวางแผน Cross-repo ต้องมองต้นทุนรวมของทุกทีม ไม่ใช่แค่ความง่ายของทีมต้นทาง แต่การรวมศูนย์งาน Migration ก็มีต้นทุนและอาจใช้ไม่ได้กับลูกค้าภายนอกทั้งหมด

### Policies That Scale Well — Beyoncé Rule

**[จากหนังสือ]** Google มีนโยบายที่ผลกระทบจากการเปลี่ยน Infrastructure ควรถูกตรวจพบผ่าน **Shared CI Tests** แทนที่จะให้ผู้ดูแล Infrastructure วิ่งถามทุกทีมถึงขั้นตอนทดสอบเฉพาะทางที่ไม่เคยรวมไว้ใน CI

ใจความไม่ใช่ “CI สมบูรณ์แบบ” แต่คือ **ทำให้ความคาดหวังที่สำคัญมองเห็นและทดสอบซ้ำได้** พร้อมแชร์ความรู้จากผู้เชี่ยวชาญให้หลายทีมเข้าถึง

### Compiler Upgrade — บทเรียนจากงานที่เลื่อนมานาน

Google เล่าการอัปเกรด Compiler ปี 2006 ที่ยากมาก เพราะไม่ได้เปลี่ยนมาหลายปี มีพฤติกรรมเก่าที่ถูกพึ่งพาโดยไม่รู้ตัว และขาดระบบ Tests ที่ครอบคลุม

ภายหลังการลงทุนใน Automation, Consistency, Expertise, Routine Upgrades และ Policies ช่วยให้งานลักษณะนี้ทำซ้ำง่ายขึ้น

**[My Engineer]** อย่าตีความว่าต้อง Upgrade ทุกสัปดาห์ตาม Google; ให้ดูว่าการ Upgrade ที่จำเป็นมี Cost, Risk และวิธีตรวจสอบอย่างไร

### Shifting Left — ตรวจพบข้อผิดพลาดให้เร็ว

**[จากหนังสือ]** ปัญหาที่ตรวจเจอตอน Design, Static Analysis, Review หรือ CI มักแก้ถูกกว่าปัญหาที่เจอหลัง Deploy เพราะต้นทุนการแก้และประสานงานน้อยกว่า

**[My Engineer]** Technical Discovery, Design Review และ Testing จึงควรช่วยค้น Critical Errors ก่อนส่งงาน ไม่ใช่สร้าง Checklist ยาว ๆ แบบไม่ดูความเสี่ยง

**ข้อจำกัด:** Tests ต้นทางไม่แทน Observability หรือการรับมือ Incident ใน Production

## 4. Trade-offs and Costs — การตัดสินใจต้องคิดต้นทุนหลายด้าน

**[จากหนังสือ]** การตัดสินใจไม่ควรจบที่ “หัวหน้าบอกให้ทำ” ควรมีเหตุผล Owner และช่องทางทบทวน โดย Cost ไม่ได้หมายถึงแค่เงิน แต่รวมถึง

- เงินและทรัพยากร Compute
- เวลาทำงานและแรงของคน
- ต้นทุนการดำเนินการหนึ่งครั้ง (Transaction Cost)
- ต้นทุนจากทางเลือกที่ไม่ได้ทำ (Opportunity Cost)
- ผลกระทบต่อผู้คนและสังคม

ทั้งนี้ข้อมูลเชิงตัวเลขสำคัญ แต่สิ่งที่วัดยาก เช่น คุณภาพของ API หรือผลกระทบต่อคน ก็ยังสำคัญ ต้องใช้ Judgment อย่างรับผิดชอบ

### Example: Markers — ประหยัดผิดจุด

Google ใช้ตัวอย่างปากกา Whiteboard ที่มีต้นทุนถูก แต่การขาดอุปกรณ์อาจขัดจังหวะการทำงานของ Engineer ซึ่งมีต้นทุนรวมสูงกว่า

**[My Engineer]** Process หรือ Approval ที่ดูเหมือนควบคุมต้นทุน อาจกลับสร้าง Waiting Time และ Context Switching ที่แพงกว่า

### Example: Distributed Builds — แก้ปัญหาหนึ่งอาจสร้างอีกปัญหาหนึ่ง

Google เปลี่ยนจาก Build บนเครื่องแต่ละคนไปสู่ระบบ Distributed Build ช่วยลดเวลารอและเพิ่มประสิทธิภาพการใช้ทรัพยากรร่วมกัน

แต่เมื่อการ Build เร็วขึ้น คนกลับไม่รู้สึกถึงต้นทุนของ Dependencies ที่บวม ทำให้การใช้ทรัพยากรเพิ่มโดยไม่มีแรงจูงใจจะลด

**[My Engineer]** หลังเลือก Solution แล้วต้องดู **Second-order Effects** ไม่ใช่แค่ตรวจว่าเป้าหมายระยะสั้นสำเร็จหรือไม่

### Time vs Scale — จะใช้ Dependency เดิมหรือ Fork?

Fork อาจช่วยควบคุมพฤติกรรมและเพิ่มความเร็วในการแก้ปัญหาเฉพาะทาง แต่ถ้าทุกทีม Fork กันหมด การอัปเดต Security และดูแลโค้ดร่วมจะยากขึ้น

**[My Engineer]** นี่คือตัวอย่าง Trade-off ที่ไม่มีคำตอบเดียว ใช้เวลาที่คาดว่าจะดูแล ขอบเขต Dependency และผลกระทบต่อผู้ใช้ประกอบกัน

### Revisiting Decisions — เปลี่ยนความเห็นเมื่อหลักฐานเปลี่ยน

การตัดสินใจที่เหมาะในอดีตอาจไม่เหมาะในวันนี้ เพราะข้อมูล ข้อจำกัด หรือเทคโนโลยีเปลี่ยน

**[My Engineer]** ADR และ Design Summary ที่ดีควรบันทึกสมมติฐานและเงื่อนไขที่ทำให้เรากลับมาทบทวน ไม่ควรถือว่าตัดสินใจไปแล้วเปลี่ยนไม่ได้

## 5. Engineering ไม่ได้เหนือกว่า Programming เสมอไป

**[จากหนังสือ — ตอนท้ายและ Conclusion]** ผู้เขียนย้ำว่าไม่ได้จัดลำดับคุณค่าของคนหรือโปรเจกต์ โค้ดอายุสั้นสองวันไม่จำเป็นต้องลงทุนใน CI/CD, Migration หรือ Dependency Governance เท่าระบบอายุสิบปี

ประเด็นคือ **เลือก Practices ให้เหมาะกับอายุระบบ จำนวนคน และผลกระทบของการตัดสินใจ**

**ข้อสังเกตจากเชิงอรรถ:** อายุระบบในที่นี้คือ *ช่วงที่ยังต้องดูแลและส่งมอบคุณค่า* ไม่ใช่ระยะเวลา Process ทำงานหนึ่งครั้ง เรื่องเล่าหรือค่าตัวเลขในหนังสือปี 2020 ไม่ควรถือเป็น Benchmark ปัจจุบันโดยไม่ตรวจสอบใหม่

## 6. Candidate Principles Registry — ยังไม่ Approve

ชื่อและ ID ด้านล่าง **My Engineer เป็นคนสังเคราะห์** ไม่ใช่ชื่อ Principles ที่ผู้เขียนกำหนดเป็นทางการ

| ID | Candidate Principle | ใช้กับอะไร | ข้อจำกัด |
| --- | --- | --- | --- |
| **EF-G01** | ออกแบบตามอายุที่คาดว่าจะดูแล Software | กำหนดระดับคุณภาพและการลงทุน | อายุระบบคาดผิดได้; Overengineering |
| **EF-G02** | รักษาความสามารถในการเปลี่ยนแปลง | Dependency Upgrade, Safe Changes | ต้นทุนดูแลโครงสร้าง; อย่าเปลี่ยนเพื่อความใหม่ |
| **EF-G03** | คำนึงถึง Observable Behavior และ Compatibility | API, Contract, Migration | ไม่ได้แปลว่าทุกพฤติกรรมต้องรักษาตลอดไป |
| **EF-G04** | ทำให้งานที่เกิดซ้ำ Scale ได้อย่างยั่งยืน | CI, Upgrade, Cross-team Process | Centralization และ Tooling มีต้นทุน |
| **EF-G05** | ทำให้สิ่งที่สำคัญตรวจจับได้ผ่าน Feedback อัตโนมัติ | Tests, CI, Regression Prevention | Tests ไม่ครอบคลุมทุกอย่างและอาจ Flaky |
| **EF-G06** | ตัดสินใจโดยมองต้นทุนรวมและทบทวนได้ | Architecture, Leadership, Delivery | วิเคราะห์นานเกินไปหรือใช้ตัวเลขปลอม |

### ลงลึก EF-G03 — Observable Behavior & Compatibility

**Layer A: Understanding** เมื่อผู้ใช้จำนวนมากเห็นผลลัพธ์ของ API ซ้ำ ๆ บางคนอาจเขียนระบบพึ่งพาพฤติกรรมนั้นโดยไม่รู้ว่ามันไม่ได้รับประกัน เช่น Response เรียงลำดับตาม Hash Map แล้ว Client ตีความลำดับเป็น Priority

**Layer B: Engineering Judgment** ใช้ตอนแก้ API, Schema, Runtime หรือเปลี่ยนการ Serialization แต่ไม่ต้องทำทุกพฤติกรรมให้เป็นสัญญาถาวร วิธีลดความเสี่ยง ได้แก่ Consumer Contract Tests, Staged Rollout, Deprecation Window และการสื่อสารกับ Owner

**Layer C: Evidence & Evolution** อ้างอิง Chapter 1 หัวข้อ “Hyrum’s Law” และ “Example: Hash Ordering” โดยตรง การนำไปตั้งเป็นกฎกลางยังต้องตรวจแหล่งวิจัยหรือหลักปฏิบัติอื่นเพิ่ม ความมั่นใจสูงว่าเป็นสิ่งที่บทนี้พูด แต่ **ยังไม่ได้ประเมินความเหมาะสมเป็นกฎสากล**

### ลงลึก EF-G06 — Full-Cost, Revisable Decisions

**Layer A: Understanding** ก่อนเลือก Solution ให้มองต้นทุนของเงิน Compute เวลาคน การประสานงาน โอกาสที่เสียไป และผลกระทบต่อผู้ใช้ ไม่ใช่แค่ Cost ที่วัดง่าย ตัวอย่าง Distributed Builds แสดงว่าระบบที่ช่วยประหยัดเวลาก็สร้างค่าใช้จ่ายแบบใหม่ได้

**Layer B: Engineering Judgment** ใช้กับ Architecture Decision, Build Tool, Dependency Strategy หรือ Team Policy ที่เปลี่ยนยาก แต่ไม่ต้องบังคับให้การแก้ Bug เล็ก ๆ เขียน ADR เต็มรูปแบบ ควรระบุ Owner, Alternatives, Assumptions และ Trigger ในการทบทวน

**Layer C: Evidence & Evolution** อ้างอิงหัวข้อ “Trade-offs and Costs”, “Distributed Builds”, “Deciding Between Time and Scale” และ “Revisiting Decisions” ของบทที่ 1 ข้อมูลอิสระและผล Pilot ของ My Engineer ยังไม่ครบ จึงเป็น **Candidate** เท่านั้น

## 8. ประเด็นที่ต้องวิจารณ์ก่อนรับเป็นหลักการกลาง

1. **บริบท Scale:** Google มีจำนวน Engineer และเครื่องมือส่วนกลางมหาศาล ทีมเล็กอาจไม่คุ้มกับนโยบายแบบเดียวกัน
2. **ความใหม่ของข้อมูล:** หนังสือปี 2020 ต้องเทียบกับ Tools, AI-Assisted Engineering และปัญหาซัพพลายเชนปัจจุบัน
3. **ไม่มีหลักฐานเชิงตัวเลขของเรา:** ยังบอกไม่ได้ว่า Workflow ของ My Engineer ทำให้ Lead Time หรือ Defect Rate ดีขึ้นเท่าไร
4. **Hyrum’s Law:** ใช้เพื่อเตือนเรื่อง Hidden Dependencies ไม่ใช่เหตุผลให้ห้ามเปลี่ยน API
5. **Shift Left:** ตรวจเร็วมีประโยชน์ แต่ Production Observability ยังจำเป็น
6. **รวมศูนย์ไม่ใช่คำตอบเสมอ:** ระบบและคนกลางอาจกลายเป็น Bottleneck ต้องพิสูจน์ก่อน Standardize
