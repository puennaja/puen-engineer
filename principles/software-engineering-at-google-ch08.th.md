## ใจความสำคัญ

**[จากหนังสือ]** Style Guide ของ Google ไม่ใช่แค่เรื่องจัดเว้นวรรคหรือชื่อ Variable แต่รวมข้อกำหนดบังคับเกี่ยวกับการเขียน Code ของแต่ละภาษา โดยแยก **Rules = ต้องทำ** (ยกเว้นเมื่อได้รับอนุญาต) ออกจาก **Guidance = ควรทำ** (ใช้ Judgment ได้)

กฎมีไว้ช่วยให้ Codebase ขนาดใหญ่ที่ต้องดูแลยาวนานเข้าใจง่าย ปลอดภัย และทำงานร่วมกันได้ แต่กฎทุกข้อสร้างภาระในการเรียนรู้ ดูแล และตรวจสอบด้วย ดังนั้นกฎต้องคุ้มกับต้นทุน มีข้อยกเว้นที่มีเหตุผล และสามารถเปลี่ยนได้

**[My Engineer]** อย่าปนคำว่า Principle, Rule, Guidance และ Practice:
- **Principle:** เหตุผลพื้นฐานที่ใช้ช่วยตัดสินใจ
- **Rule:** สิ่งที่บังคับทำภายใน Scope ที่กำหนด
- **Guidance:** คำแนะนำที่ปรับตามบริบทได้
- **Practice:** วิธีทำงานที่ช่วยให้บรรลุ Principle

การอ่านหนังสือเจอคำแนะนำหนึ่งข้อ **ไม่ได้แปลว่าต้องเพิ่มกฎใน AGENTS.md**

## 1. ทำไมต้องมีกฎ? — Why Have Rules?

**[จากหนังสือ]** กฎใช้ส่งเสริมพฤติกรรมที่องค์กรให้ความสำคัญ เช่น ความปลอดภัย ประสิทธิภาพ Memory ความอ่านง่าย หรือ Consistency แต่คำว่า “ดี” ขึ้นกับข้อจำกัดของแต่ละองค์กร ไม่ใช่มีคำตอบเดียวตลอดกาล

กฎที่ใช้ร่วมกันทำให้ Engineer สื่อสารด้วยรูปแบบคุ้นเคย ลดการถกเถียงเดิม ๆ และช่วยให้คนที่มาจากทีมอื่นเข้ามาอ่าน Code ได้เร็วขึ้น แต่ต้องยอมแลกกับอิสระในการเลือกทางออกบางอย่าง

**[My Engineer]** ก่อนตั้งกฎใหม่ ให้ถามว่า “เรากำลังแก้ปัญหาอะไรที่เกิดขึ้นจริง?” ไม่ใช่ “เราน่าจะมีกฎเพิ่มอะไรดี?”

## 2. หลักห้าข้อในการสร้างกฎ — Guiding Principles

นี่คือ **หัวข้อหลักที่ผู้เขียนระบุในบทจริง** ไม่ใช่การตั้งชื่อใหม่ของเรา:

### 2.1 Rules must pull their weight — กฎต้องคุ้มกับภาระ

เมื่อเพิ่มกฎ ทุกคนต้องเรียนรู้ ปรับ Code และแบกรับภาระตรวจสอบ ถ้า Engineer แค่ 1–2 คนทำผิดซ้ำ อาจคุ้มกว่าที่จะสอนหรือแก้เฉพาะจุด แทนการออกกฎทั้งบริษัท

**[My Engineer]** ถ้าใน Workflow เรามี Checklist 20 ข้อ แต่ 15 ข้อไม่มีใครใช้ตัดสินใจจริง ก็ควรลดหรือปรับ Scope ไม่ใช่ยิ่งเพิ่มรายละเอียด

### 2.2 Optimize for the reader — คิดถึงคนอ่านมากกว่าคนเขียน

โค้ดจะถูกอ่านมากกว่าถูกเขียนในระยะยาว รูปแบบที่พิมพ์สั้นอาจทำให้คนอื่นต้องไล่ Code ยาวกว่า ตัวอย่างจากหนังสือคือการใช้ Annotation/Keyword เพื่อระบุ Override และการใช้ `std::unique_ptr` กับ Move Semantics ให้เห็นการส่งต่อ Ownership ที่จุดเรียก

ผู้เขียนเชื่อมเรื่องนี้กับ **Local Reasoning**: อ่าน Code ใกล้ ๆ จุดที่ทำงานแล้วควรเข้าใจ Intent สำคัญได้ โดยไม่ต้องกระโดดไปเปิด Implementation ทุก Function

**[My Engineer]** เรื่องนี้นำมาทบทวน Code Review ได้ แต่ห้ามแปลงเป็นกฎว่า “โค้ดยาวดีกว่าโค้ดสั้น” เสมอไป เพราะ Clarity ขึ้นกับ Context

### 2.3 Be consistent — สม่ำเสมอเพื่อลดต้นทุนการทำงานร่วมกัน

Consistency ช่วยให้ Engineer ย้ายไปทำ Repo อื่นได้เร็ว เครื่องมือเข้าใจโครงสร้างเหมือนกัน และลดการเถียงเรื่อง Formatting/Import Order

อย่างไรก็ตาม **Consistency ไม่จำเป็นต้องสมบูรณ์แบบทั่วทั้งบริษัท** โดยเฉพาะ Codebase ที่เก่าและใหญ่มาก หนังสือพูดถึงลำดับจากรูปแบบที่ใช้อยู่ในไฟล์ → ทีม → โปรเจกต์ → ทั้งองค์กร เมื่อไม่มีข้อกำหนดที่สูงกว่าบังคับ และยังพิจารณามาตรฐานของ Community ภายนอกด้วย

**กรณีศึกษา:** Google เคยให้ Python ใช้ Indent สองช่องเพื่อเข้ากับ C++ แต่เมื่อโลกของ Python ภายนอกใช้สี่ช่อง การยึดมาตรฐานเดิมทำให้ต้องแปลงไปมา และ Starlark จึงเลือกสี่ช่อง

**[My Engineer]** อย่าบังคับให้ Go กับ TypeScript ใช้ Convention แบบเดียวกันจนขัดกับ Tool/Community ของแต่ละภาษา

### 2.4 Avoid error-prone and surprising constructs — หลีกเลี่ยงสิ่งซับซ้อนที่คาดเดายาก

ผู้เขียนยก Python Reflection เช่น `getattr` ที่รับชื่อ Field เป็น String ถ้า String มาจาก RPC หรือ Data Store อาจทำให้ค้น Usage ยาก ตรวจสอบความปลอดภัยยาก และเกิด Bug ที่มองไม่เห็น

ถึง Expert จะใช้ฟีเจอร์ขั้นสูงได้ถูกต้อง ก็ต้องนึกถึง Engineer คนใหม่และ SRE ที่เข้ามา Debug ในวันเกิด Incident

**[My Engineer]** อย่า Ban Dynamic Feature ทุกประเภทโดยไม่มีเหตุผล ให้ประเมินความอ่านง่าย ผลกระทบด้าน Security และช่องทางตรวจสอบก่อน

### 2.5 Concede to practicalities — ยอมให้ยืดหยุ่นเมื่อมีเหตุผลจริง

หนังสือยก Exception ที่เกี่ยวกับ Performance, Interoperability และ Generated Code เช่น Naming ที่เลียนแบบ Standard Library หรือข้อยกเว้นสำหรับ Windows Platform

**[My Engineer]** กฎที่ไม่มีช่องทาง Exception อาจบังคับให้ Engineer ใช้ทางออกที่แย่กว่า แต่ Exception ต้องมีเหตุผลและ Owner ไม่ใช่ใครอยากฝืนกฎก็ฝืนได้

## 3. อะไรควรอยู่ใน Style Guide? — The Style Guide

หนังสือแยกออกเป็นสามกลุ่ม:

| ประเภทกฎ | เป้าหมาย | ตัวอย่าง |
| --- | --- | --- |
| **Avoiding danger** | ป้องกัน Feature/Pattern ที่เสี่ยงหรือใช้ให้ถูกยาก | Concurrency, Exception, Access Control |
| **Enforcing best practices** | ส่งเสริม Maintainability และความอ่านง่าย | Comments ที่บอก Intent, File Structure, Naming |
| **Building consistency** | เลือก Convention กลางเพื่อหยุดข้อถกเถียงซ้ำ | Indentation, Import Order, Formatting |

**กรณีศึกษา `std::unique_ptr`:** Google เคยห้ามใช้ช่วงแรกของ C++11 เพราะคนยังไม่เข้าใจ Move Semantics ต่อมาเมื่อทีมเข้าใจมากขึ้นและเห็นว่า Ownership ชัดเจนขึ้น กฎก็ถูกเปลี่ยนให้ใช้ได้

**ข้อสรุป:** การห้ามเทคโนโลยีใหม่อาจเป็นมาตรการชั่วคราวระหว่างเรียนรู้ ไม่ควรถือว่าเทคโนโลยีนั้นไม่ดีตลอดไป

Style Guide ไม่จำเป็นต้องครอบคลุม Best Practice ทุกเรื่อง และไม่สามารถทำให้มือใหม่กลายเป็นผู้เชี่ยวชาญด้วย Checklist เพียงฉบับเดียว

## 4. กฎเปลี่ยนได้ — Changing the Rules

**[จากหนังสือ]** กฎที่เคยถูกต้องอาจล้าสมัยเมื่อ Language, Ecosystem หรือวิธีใช้ Code เปลี่ยน สัญญาณที่ควรทบทวน เช่น คนหาทางเลี่ยงกฎบ่อย Tool ที่บังคับใช้แพงขึ้น หรือมีคำขอ Exception ที่สมเหตุสมผลซ้ำ ๆ

### ตัวอย่าง Python CamelCase → snake_case

Google เคยกำหนดให้ Method ใน Python ใช้ CamelCase เพราะ Python ช่วงแรกสัมพันธ์กับ C++ มาก แต่เมื่อมี Python Application และ Open-source Integration เพิ่มขึ้น Convention นี้กลับสร้างความยุ่งยาก เทียบกับ Community ที่ใช้ snake_case

ทีมผู้กำกับ Style Guide จึงยอมให้ใช้ snake_case แบบมีเงื่อนไข เช่น เลือกให้สอดคล้องภายในไฟล์และไม่บังคับแปลง Code เก่าทันที

**[My Engineer]** เวลาออกกฎ ต้องบันทึกว่าเหตุผลเดิมคืออะไร เงื่อนไขใดจะทำให้เปลี่ยนได้ และใครตัดสินใจ ไม่ใช่ถือว่ากฎที่เคย Approved ต้องถูกตลอดไป

### กระบวนการเปลี่ยนกฎและ Rule Owner

Google เปิดให้ Engineer เสนอการเปลี่ยนจากปัญหาจริง จากนั้น Community พิจารณาข้อดีข้อเสีย และ **Style Arbiters** ซึ่งเป็นผู้เชี่ยวชาญประจำภาษาตัดสินขั้นสุดท้ายโดยดู Trade-offs ไม่ใช่ความชอบของแต่ละคน

สำหรับ My Engineer เราอาจกำหนด Owner ตามขนาดทีม ไม่จำเป็นต้องตั้งคณะกรรมการตั้งแต่ทำงานคนเดียว

### Exceptions — ข้อยกเว้นที่ตรวจสอบได้

กฎตั้งมาสำหรับกรณีทั่วไป แต่บางกรณีมีเหตุผลเฉพาะ:
- C++ Macro ที่ควรมี Prefix ป้องกัน Name Collision ไม่ควรยกเว้นเพียงเพราะชื่อยาว
- Transparent Wrapper อาจมีเหตุผลให้ใช้ Implicit Conversion แม้โดยทั่วไปมีความเสี่ยง

**[My Engineer]** ถ้ามีการขอ Exception แบบสมเหตุสมผลบ่อย อาจแปลว่าควรปรับกฎ; ถ้าขอเพื่อความสะดวกอย่างเดียว อาจไม่ควรอนุญาต

## 5. Guidance ไม่ใช่ Rule — Guidance

Google มี Primers, Tips สั้น ๆ ที่มาจากปัญหาจริง, Training สำหรับคนเข้าทีม และ Reference ที่ช่วยหาความรู้เฉพาะงาน สิ่งเหล่านี้เป็น **คำแนะนำ** ไม่ได้บังคับเหมือน Style Guide

**[My Engineer]** นี่ช่วยอธิบายว่าทำไมไม่ควรเอาทุก Principle หรือคำแนะนำลง `AGENTS.md`:
- `principles/` เก็บเหตุผล Trade-offs และหลักฐาน
- `practice/` หรือ Documentation เก็บคำอธิบายและตัวอย่าง
- `AGENTS.md` เก็บกฎที่ตกลงบังคับใช้และ Scope ชัด
- `puen-stack` เก็บ Skill/Tool หลังพิสูจน์ว่าคุ้มค่าจริง

**นี่เป็นข้อเสนอด้านโครงสร้างของเรา ไม่ใช่คำสั่งจากหนังสือ**

## 6. การบังคับใช้กฎ — Applying the Rules

**[จากหนังสือ]** มีทั้งการสอน Code Review และ Tooling แต่งานที่ตรวจสอบได้แน่นอนควรให้เครื่องมือช่วย เพราะลดภาระความจำ ลดการใช้ดุลยพินิจไม่สม่ำเสมอ และลดการเถียงเดิม ๆ

### Error Checkers

เครื่องมืออย่าง `clang-tidy` และ `Error Prone` ตรวจการใช้ API หรือรูปแบบ Code ที่เสี่ยงได้ ตัวเลขสัดส่วน Rule ที่ตรวจอัตโนมัติได้ซึ่งหนังสือยก เป็นการสำรวจภายในในอดีต ไม่ใช่เปอร์เซ็นต์รับประกันสำหรับโปรเจกต์เรา

### Code Formatters / gofmt

`gofmt` ทำให้โค้ด Go มีรูปแบบเดียวตั้งแต่ต้น ลด Review ที่เถียงเรื่อง Format และช่วยให้ Tool เขียน Code อัตโนมัติสร้าง Diff ที่อ่านง่าย

ส่วน `buildifier` เป็นกรณีที่ต้อง Format BUILD Files เดิมจำนวนมาก แสดงว่า Standardization ในระบบเก่ามี Migration Cost

**[My Engineer]** Formatter/Lint ที่แน่นอนควรใช้เครื่องมือตรวจ แต่ Review ความถูกต้องเชิงธุรกิจ Architecture Trade-off และข้อยกเว้นต้องใช้วิจารณญาณของคน การให้ LLM ตรวจด้วยข้อความไม่ใช่ Deterministic Enforcement

### ทำไมไม่บังคับจำนวนบรรทัดใน Pull Request?

หนังสือยกตัวอย่างว่า การแก้หนึ่งบรรทัดเหมือนกันหลายร้อยไฟล์อาจตรวจง่าย แต่ Logic ซับซ้อนแค่ 20 บรรทัดกลับเสี่ยงมาก การบังคับกฎว่า PR มากกว่า X บรรทัดให้ Reject อัตโนมัติจึงอาจผิดเป้าหมาย

**[My Engineer]** ให้ Reviewer ประเมิน Complexity และ Scope ตามบริบท แทนการยึดตัวเลขอย่างเดียว

## 7. บทสรุปและสิ่งที่เราไม่ควรเชื่อตามโดยอัตโนมัติ

**[จากหนังสือ]** Rules/Guidance ต้องช่วยให้ดูแลระบบระยะยาวและรองรับ Scale; ต้องใช้ข้อมูลเพื่อปรับกฎ; ไม่ใช่ทุกอย่างต้องเป็นกฎ; Consistency สำคัญ; และควร Automation เมื่อเหมาะสม

**สิ่งที่ต้องวิจารณ์ [My Engineer]:**
1. Google มีขนาดและเครื่องมือส่วนกลางที่ทีมเล็กอาจไม่คุ้มลงทุนตาม
2. การห้ามเด็ดขาดบางเรื่องอาจทำให้คนหลบกฎหรือไม่กล้าลองวิธีใหม่
3. Automation ของข้อกำหนดเชิงอัตวิสัยอาจมี False Positives มาก
4. Rule Owner ส่วนกลางอาจเป็น Bottleneck ถ้า Scope และอำนาจไม่ชัด
5. บทนี้เป็นประสบการณ์ขององค์กรหนึ่ง ไม่ใช่หลักฐานวัดผลใน My Engineer

### EF-G07 — กฎต้องคุ้มต้นทุน: Knowledge Model

**Understanding:** กฎหนึ่งข้อมี Cost ต่อทุกคนที่เกี่ยวข้อง ทั้งการเรียนรู้ การปฏิบัติและการดูแล ดังนั้นควรแก้ปัญหาที่สำคัญ เกิดซ้ำ หรือเสี่ยงสูง ไม่ใช่ความชอบส่วนตัว

**Engineering Judgment:** ใช้เมื่อตัดสินใจเพิ่มข้อบังคับใน `AGENTS.md`, Coding Convention หรือ CI Gate ไม่ควรตัดกฎที่ป้องกันข้อมูลรั่วไหลเพียงเพราะเกิดไม่บ่อย ทางเลือกอื่นคือ Guideline, Rule เฉพาะ Scope, Training หรือ Pilot

**Evidence & Evolution:** อ้างอิง “Rules must pull their weight” และ “Changing the Rules” โดยตรง แต่ยังต้องดูหลักฐานอื่น/ผลทดลองภายใน ความมั่นใจว่าเป็นแนวคิดของผู้เขียนสูง ส่วนการใช้เป็นกฎของ My Engineer ยังไม่ได้ประเมิน **สถานะ: Candidate**

### EF-G12 — ใช้ Automation ให้ถูกประเภท: Knowledge Model

**Understanding:** งานตรวจซ้ำที่เป็นกฎแน่นอน เช่น Formatting ลดความคลาดเคลื่อนและงานจุกจิกได้ผ่าน Tool ส่วน LLM Review แบบภาษาธรรมชาติไม่เท่ากับการตรวจที่ให้ผลคงที่

**Engineering Judgment:** ใช้ Formatter, Linter, CI Check สำหรับข้อกำหนดที่ตรวจได้จริง ส่วน Architecture, Intent, Trade-off และ Exception ให้คนร่วม Review หลีกเลี่ยงการตั้ง Hard Gate ด้วย Heuristic ที่ยังไม่เคยทดสอบ

**Evidence & Evolution:** อ้างอิง “Applying the Rules”, “Code Formatters” และ “Case Study: gofmt” การประยุกต์ใช้กับ AI Coding ต้องทดสอบเพิ่มเติม เพราะบทปี 2020 ไม่ได้พิสูจน์เรื่อง Agentic Workflows **สถานะ: Candidate**

## 9. ข้อเสนอสถาปัตยกรรม Knowledge ของ My Engineer (ยังไม่ Approve)

| ประเภท | เก็บที่ไหน | การกำกับ |
| --- | --- | --- |
| Principle — เหตุผลและข้อจำกัด | `principles/` | Candidate → Reviewed → Accepted |
| Guidance — คำอธิบายและตัวอย่าง | `practice/` / เอกสารที่เกี่ยวข้อง | ใช้ Judgment |
| Rule — สิ่งที่ต้องทำ | `AGENTS.md` เฉพาะขอบเขต / CI Config | ต้องรับรอง Scope/Owner |
| Tool/Skill — วิธีทำอัตโนมัติ | `puen-stack` | ทดลองและพิสูจน์ก่อน |

ถ้าเราจะใช้ Rule Registry ในอนาคต ข้อมูลขั้นต่ำที่กูเสนอ ได้แก่:
- Rule ต้องการบังคับอะไร
- แก้ปัญหาอะไรและมีหลักฐานอะไร
- ใช้กับ Project/Language ไหน ใครรับผิดชอบ
- ตรวจอย่างไร
- ขอ Exception อย่างไร
- เกิดเงื่อนไขอะไรแล้วควรกลับมาทบทวน

**ยังไม่เปลี่ยน `AGENTS.md` หรือสร้าง Skill ใดจากการอ่านครั้งนี้**

## 10. อ่านอะไรต่อและ Review อย่างไร?

- เริ่ม Review **EF-G07** กับ **EF-G12** เพราะเกี่ยวกับ Principles Registry, Agent Instructions และ Quality Automation โดยตรง
- ลองประเมินกฎจริงหนึ่งข้อใน `AGENTS.md` ว่าแก้ปัญหาอะไรและคุ้มกับภาระไหม
- ถ้าต้องการลดเอกสารซ้ำ อ่าน Chapter 10 — Documentation ต่อ
- ถ้าต้องการวัดว่า Workflow ช่วยทีมจริงไหม อ่าน Chapter 7 — Measuring Engineering Productivity
