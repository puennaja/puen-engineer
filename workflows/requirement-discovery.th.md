# กระบวนการค้นหาและทำความเข้าใจความต้องการ (Requirement Discovery) — v1.0

- **สถานะ:** Accepted — กระบวนการของ My Engineer Track A
- **เวอร์ชัน:** 1.0
- **พื้นฐาน:** [Feature Delivery Lifecycle](./feature-delivery-lifecycle.th.md)
- **กิจกรรมถัดไป:** [Technical Discovery](./technical-discovery.th.md)
- **บริบทตัวอย่าง:** แอปการเงินส่วนบุคคลสมมติ ไม่ใช่ Requirement ที่ยืนยันแล้ว

## วัตถุประสงค์
หลีกเลี่ยงการเริ่ม Implement จากคำขอที่ยังไม่เข้าใจจริง ค้นหาปัญหา ผู้ใช้ ผลลัพธ์ที่ต้องการ เงื่อนไขการยอมรับ ขอบเขต และความไม่แน่นอน ก่อนตัดสินใจเลือกโซลูชัน การทำ Discovery เป็นการลดความเสี่ยง ไม่ใช่พิธีกรรมเพื่อเติมเอกสารให้ครบ

## หลักการ
1. เริ่มจากปัญหาและผลลัพธ์ ไม่เริ่มจากฟีเจอร์หรือวิธี Implement
2. แยก **ข้อเท็จจริง / สมมติฐาน / คำถามที่ยังไม่รู้** และระบุหลักฐาน
3. ระบุผู้ได้รับผลกระทบ ผู้ตัดสินใจ และเจ้าของ Requirement
4. ทำให้ Scope, Out-of-scope, Constraint และ Acceptance Criteria มองเห็นได้
5. ค้นหา Happy Path, Alternate Path, Edge Case และ Failure Case ที่สำคัญ
6. ถามคำถามที่เปลี่ยนการตัดสินใจจริง หลีกเลี่ยงการประชุมหรือเอกสารเกินความจำเป็น
7. ปรับระดับความละเอียดตามความเสี่ยง และย้อนกลับมา Discovery ได้ระหว่างพัฒนา

## กิจกรรมหลัก
| กิจกรรม | คำถาม | ผลลัพธ์ |
| --- | --- | --- |
| เข้าใจคำขอ | ใครเจอปัญหา อะไรเป็นแรงจูงใจ และเหตุใดจึงสำคัญ? | Problem Statement และผู้เกี่ยวข้อง |
| สำรวจสภาพปัจจุบัน | ผู้ใช้ทำอะไรอยู่จริง มีหลักฐานใด? | As-is / หลักฐานและข้อจำกัด |
| ทำให้ผลลัพธ์ชัดเจน | ความสำเร็จและพฤติกรรมที่ต้องการคืออะไร? | Outcome และ Acceptance Examples |
| กำหนดขอบเขต | อะไรต้องทำ อะไรยังไม่ทำ และอะไรยังไม่แน่ชัด? | Scope / Non-goals / Assumptions |
| สำรวจสถานการณ์ | ทางเลือก กรณีผิดพลาด สิทธิ์ ข้อมูลขอบ และข้อยกเว้นคืออะไร? | Use Cases / Edge Cases |
| สรุปและส่งต่อ | รู้พอให้ Technical Discovery หรือยัง? ใครตัดสินใจ? | Discovery Summary และ Next Action |

กิจกรรมเหล่านี้ไม่จำเป็นต้องทำเรียงเป็น Waterfall และไม่จำเป็นต้องใช้เอกสารเต็มรูปแบบสำหรับงานเล็ก

## เทคนิคการตั้งคำถาม
- **ผู้ใช้และคุณค่า:** ใครได้ประโยชน์ และเราจะรู้ได้อย่างไรว่าดีขึ้น?
- **พฤติกรรม:** Trigger คืออะไร Input/Output เป็นอย่างไร?
- **ขอบเขต:** มีกรณีใดที่ไม่รองรับ? ต้องรักษาพฤติกรรมเดิมอะไร?
- **ความถูกต้อง:** ข้อมูลซ้ำ ข้อมูลหาย สถานะระหว่างทาง และ Race Condition ส่งผลอย่างไร?
- **ความปลอดภัย:** สิทธิ์เข้าถึง Privacy, Retention และ Audit สำคัญแค่ไหน?
- **การยอมรับ:** จะยืนยันได้อย่างไรโดยไม่อาศัยเพียงความรู้สึกว่าเสร็จ?
- **เจ้าของการตัดสินใจ:** ใครตอบคำถามที่ส่งผลต่อ Scope หรือ Priority?

## Artifact หลัก: Discovery Summary
เก็บใน Ticket หรือ Markdown ที่อ้างอิงจาก Ticket เดิม ไม่สร้างเอกสารซ้ำซ้อนโดยไม่จำเป็น

~~~markdown
# Requirement Discovery — <Feature>
Status: Draft | Ready for technical discovery | More discovery needed | Blocked
Owner / Decision maker:
Source / Requester:
Date / Evidence:

## Problem and desired outcome
ใครเจอปัญหาอะไร และคาดหวังผลลัพธ์อย่างไร?

## Users and context
ผู้ใช้งาน กระบวนการปัจจุบัน และหลักฐาน

## Scope and boundaries
In scope / Out of scope / Constraints

## Use cases and acceptance examples
Trigger | Given | When | Then | Exception

## Assumptions and open questions
Question | Impact | Owner | Validation

## Decision and handoff
สิ่งที่ตกลงแล้ว สิ่งที่ยังไม่รู้ และขั้นตอนถัดไป
~~~

## เกณฑ์พร้อมส่งต่อ
- อธิบายปัญหาและผลลัพธ์ที่ต้องการได้
- มีขอบเขตและตัวอย่างพฤติกรรมที่สำคัญพอให้เริ่มสำรวจทางเทคนิค
- ข้อสมมติและคำถามที่อาจเปลี่ยน Scope ถูกระบุ พร้อมผู้รับผิดชอบ
- ไม่แสร้งว่า Acceptance Criteria ครบแล้วเมื่อยังมีช่องว่าง

**ผลลัพธ์ที่เป็นไปได้:** ส่งต่อ Technical Discovery, ทำ Product/Requirement Spike, ขอคำตอบเพิ่ม, หรือชะลอ/ตัด Scope

## บทบาท
Product Owner หรือเจ้าของปัญหาตัดสินใจด้านคุณค่าและ Priority; Engineer ช่วยค้นหา Edge Cases และ Feasibility Questions; Tech Lead ช่วยจัดการความเสี่ยงข้ามระบบ; QA และผู้เกี่ยวข้องช่วยระบุความสามารถในการตรวจสอบ ไม่มีบทบาทใดควรใช้ AI แทนความรับผิดชอบของคน

## ตัวอย่างสมมติ: แอปการเงินส่วนบุคคล
ความต้องการที่อาจเกิดขึ้นคือ “อยากเห็นค่าใช้จ่ายรายเดือนโดยไม่ต้องกรอกเองทั้งหมด” แต่ยังไม่รู้ว่าผู้ใช้พร้อมอัปโหลด Statement หรือไม่ ต้องตรวจสอบวิธีใช้งานจริง ความหมายของโอนเงินระหว่างบัญชี เงินคืน เงินสด ข้อมูลที่ขาด และมาตรการ Privacy ก่อนสรุปว่า CSV Import เป็น MVP

## AI ช่วยได้อย่างไร
AI ช่วยจัดหมวดคำถาม เสนอ Use Cases / Edge Cases สรุปประเด็นจากข้อมูลที่อนุญาต และตรวจช่องว่างใน Acceptance Criteria ได้ แต่ห้ามแต่งคำตอบผู้ใช้ อ้างว่ามีการอนุมัติ หรือส่งข้อมูลภายในไปยังเครื่องมือที่ไม่ได้รับอนุญาต

## การนำไปทดลองและปรับปรุง
ทดลองทั้งงานเล็กที่ย้อนกลับง่ายและงานที่มีความเสี่ยง ดูว่าคำถามสำคัญถูกค้นพบเร็วขึ้นหรือไม่ มี Rework ลดลงหรือไม่ และเอกสารสร้างภาระเกินประโยชน์หรือไม่ ผลการทดลองไม่ได้แปลว่าต้องสร้าง Skill ใหม่ทันที

**หมายเหตุ:** ฉบับภาษาไทยนี้ใช้คู่กับต้นฉบับภาษาอังกฤษ หากต้องการถ้อยคำสำหรับการอนุมัติอย่างเป็นทางการ ให้เทียบต้นฉบับ
